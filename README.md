# Deploy and Host Mission Control on Railway

Mission Control is an open-source (MIT) control plane for AI agents by builderz-labs. From one web dashboard you register agents, dispatch and queue tasks, review runs and their results, track token use and cost per agent, and keep an audit trail. It works standalone, and can also connect to an OpenClaw gateway, Claude Code, Codex and other agent runtimes.

## About Hosting Mission Control

This template deploys one service: Mission Control 2.3.0, built from this GitHub repo on the official `ghcr.io/builderz-labs/mission-control` image pinned by version and digest. Its SQLite database, generated keys and nightly backups live on a Railway volume at `/app/.data`, so redeploys and restarts keep your data. The admin account is created on first start from the generated `AUTH_PASS` variable, so the setup page is already closed when your URL goes live. A small start script fixes the volume's ownership, allows your Railway domain through Mission Control's host allow-list and starts the app as a non-root user. Railway checks `/api/health`.

## Common Use Cases

* One dashboard for tasks and runs across several AI agents and runtimes
* Track token use and cost per agent and per task
* Review, approve and audit agent work, and give agents a shared task inbox through the REST API or MCP server

### Implementation Details

**First login.** Open the Mission Control service's **Variables** tab and copy `AUTH_PASS`. Sign in at `https://YOUR-DOMAIN/login` with the username `admin` and that password. Change the password in the app afterwards if you like: changing `AUTH_PASS` later doesn't change an existing admin. For agents, scripts and the MCP server, copy the API key from **Settings** and send it as the `x-api-key` header.

**Custom domain.** Mission Control answers 403 to any host it doesn't know. The Railway domain is allowed automatically. If you add your own domain, set `MC_ALLOWED_HOSTS=YOUR-DOMAIN` on the service and redeploy.

**Agent runtimes.** No gateway is bundled. Tasks, projects, agents, schedules, webhooks, alerts and cost tracking work without one. To connect an OpenClaw gateway, use the gateway settings in the app.

**Updates.** The service builds from `aalfath/mission-control-railway-template`. When we bump the pinned Mission Control version, Railway shows an update notice in your project. Read the repo's `CHANGELOG.md`, then apply it. Database migrations run on start.

## Template contents

| File | What it does |
|---|---|
| `Dockerfile` | `FROM ghcr.io/builderz-labs/mission-control:2.3.0@sha256:695063d5f12bba3cfe1582f56f88b08a2a2bef548d57662d41d51f87e79679a5`, plus the start script |
| `railway-start.sh` | Chowns the `/app/.data` volume to the app user, adds the Railway domains to `MC_ALLOWED_HOSTS`, then runs the upstream entrypoint as uid 1001 |
| `docker-compose.test.yml` | Local test only (`AUTH_PASS=... docker compose -f docker-compose.test.yml up --build`); Railway doesn't use it |

## Variables (Mission Control service)

| Variable | Default | Notes |
|---|---|---|
| `PORT` | `3000` | Port Mission Control listens on; the public domain targets it |
| `AUTH_USER` | `admin` | Admin username created on first start |
| `AUTH_PASS` | `${{secret(24, ...)}}` | Generated admin password, used only to create the admin on first start |

`AUTH_SECRET` and `API_KEY` are generated by the app on first start and kept on the volume. Optional, not template variables: `MC_ALLOWED_HOSTS` (extra hosts such as a custom domain), Google sign-in (`GOOGLE_CLIENT_ID`) and the data-retention settings in upstream's [`.env.example`](https://github.com/builderz-labs/mission-control/blob/v2.3.0/.env.example).

## Updating

The Mission Control version is pinned in `Dockerfile` by tag and digest. A version bump is a commit to `main` with a `CHANGELOG.md` entry; deployers get Railway's update notice and choose when to apply it.
